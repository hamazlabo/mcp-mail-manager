# Requirements: mcp-mail-manager

> 要件は EARS (Easy Approach to Requirements Syntax) で記述する。
> 各要件は一意の ID を持ち、design.md / task.md から参照される。

## EARS 構文リファレンス

| パターン | 形式 |
|----------|------|
| 普遍 (Ubiquitous) | The system shall response. |
| イベント駆動 (Event-driven) | WHEN trigger, the system shall response. |
| 状態駆動 (State-driven) | WHILE state, the system shall response. |
| 望まない事象 (Unwanted behaviour) | IF condition, THEN the system shall response. |
| オプション (Optional) | WHERE feature is included, the system shall response. |

日本語で書く場合も構造を保つ:「トリガーのとき、システムは応答しなければならない」。

以下、「システム」= mcp-mail-manager 全体、「MCP サーバ」= ツールを公開する API、「同期ジョブ」= IMAP → S3 / DynamoDB の取込、「スケジューラ」= 予約送信の実行系。

## 1. 機能要件

### 1.1 同期（IMAP → S3 / DynamoDB）

### REQ-001: 定期差分同期

- **要件**: WHEN 15 分ごとの定期スケジュールが発火したとき, 同期ジョブは IMAP の全フォルダについて前回同期以降の新着メッセージを取得し、生メッセージ (RFC 5322) を S3 に、メタ情報（メッセージ ID、フォルダ、UID、件名、差出人、宛先、日時、既読・フラグ状態、添付のファイル名とサイズ）を DynamoDB に保存しなければならない。
- **理由**: 検索・閲覧を DynamoDB / S3 に対して行うため（specify.md 課題 1・決定済み事項）。
- **受け入れ基準**:
  - [ ] フォルダごとに最後に取り込んだ UID と UIDVALIDITY を保持し、次回はそれ以降の UID のみ取得する。
  - [ ] 同じメッセージを 2 回取り込んでも DynamoDB / S3 に重複が生じない（冪等）。
  - [ ] UIDVALIDITY が変わったフォルダは、そのフォルダを全件再取込する。
  - [ ] 添付ファイルの本体は S3 の生メッセージ内にのみ存在し、個別に取り出さない。

### REQ-002: 初回同期の範囲

- **要件**: WHEN あるフォルダの同期状態が存在しないとき, 同期ジョブは受信日時が過去 90 日以内のメッセージのみを取り込まなければならない。
- **理由**: 初回同期の時間と保存容量を抑える。
- **受け入れ基準**:
  - [ ] 90 日より古いメッセージは取り込まれない。
  - [ ] 初回同期完了後は REQ-001 の差分同期に切り替わる。

### REQ-003: 状態変化の反映（IMAP → DynamoDB）

- **要件**: WHEN 同期ジョブが実行されたとき, 同期ジョブは取込済みメッセージの既読 (\Seen)・フラグ (\Flagged) の変化と、フォルダからの消失（他フォルダへの移動・削除）を DynamoDB に反映しなければならない。
- **理由**: 「同期データと IMAP の不整合」を起こさない（禁止事項）。
- **受け入れ基準**:
  - [ ] メールクライアント側で既読にしたメッセージが、次回同期後に DynamoDB でも既読になる。
  - [ ] メールクライアント側でフォルダ移動したメッセージが、次回同期後に新しいフォルダとして検索できる。
  - [ ] IMAP から消えたメッセージは DynamoDB のメタ情報から削除または削除済みとしてマークされる。

### REQ-004: 同期の分割継続

- **要件**: IF 1 回の同期実行が実行時間の上限（Lambda 15 分）内に完了しない場合, THEN 同期ジョブは処理済み位置を保存して終了し、次回実行で続きから再開しなければならない。
- **理由**: 初回同期や大量受信時にデータを失わない。
- **受け入れ基準**:
  - [ ] 途中終了した同期を再実行すると、未取込分だけが取り込まれる。
  - [ ] 途中終了によって取込済みメッセージが重複・欠落しない。

### 1.2 検索・閲覧

### REQ-010: メール検索

- **要件**: WHEN AI エージェントが検索ツールを呼び出したとき, MCP サーバは DynamoDB のメタ情報に対して、フォルダ・差出人・宛先・件名キーワード・受信日時範囲・未読/フラグ状態の任意の組み合わせで絞り込み、受信日時の降順でページング付き一覧（メッセージ ID、件名、差出人、日時、既読・フラグ、添付有無）を返さなければならない。
- **理由**: specify.md 成功の定義「検索・要約・返信」。
- **受け入れ基準**:
  - [ ] 条件を 1 つも指定しない場合は全フォルダの最新メールが返る。
  - [ ] ページサイズ既定 20、最大 100。継続トークンで次ページを取得できる。
  - [ ] 検索結果に本文は含まれない。
  - [ ] 条件に一致するメールが無い場合は空一覧を返し、エラーにしない。
  - [ ] 件名・差出人のキーワードは部分一致（大文字小文字を区別しない）。日時範囲が未指定の場合は直近 90 日を既定とする。

### REQ-011: メール本文の閲覧

- **要件**: WHEN AI エージェントがメッセージ ID を指定して閲覧ツールを呼び出したとき, MCP サーバは S3 の生メッセージを解析し、ヘッダ（From/To/Cc/Date/Subject/Message-ID/In-Reply-To）、テキスト本文、添付ファイルのメタ情報（ファイル名・MIME タイプ・サイズ）を返さなければならない。
- **理由**: 要約・返信の材料を提供する。
- **受け入れ基準**:
  - [ ] text/plain パートがあればそれを返す。
  - [ ] text/plain が無く text/html のみの場合は HTML をテキスト化して返す。
  - [ ] 添付ファイルの本体は返さない。
  - [ ] 存在しないメッセージ ID の場合は「見つからない」エラーを返す。

### REQ-012: フォルダ一覧

- **要件**: WHEN AI エージェントがフォルダ一覧ツールを呼び出したとき, MCP サーバは同期済みフォルダの名前と各フォルダのメッセージ数・未読数、およびその件数を取得した同期時刻（`lastSyncAt`）を返さなければならない。
- **理由**: 移動先の指定と検索条件の把握。
- **受け入れ基準**:
  - [ ] Sent / Trash に相当する特殊フォルダが識別できる（SPECIAL-USE 属性または設定値）。

### 1.3 送信

### REQ-020: 新規メール送信

- **要件**: WHEN AI エージェントが宛先（To、任意で Cc/Bcc）・件名・本文を指定して送信ツールを呼び出したとき, MCP サーバは SMTP でプレーンテキスト (text/plain, UTF-8) メールを送信し、送信したメッセージを IMAP の Sent フォルダに APPEND しなければならない。
- **理由**: 成功の定義「返信できる」。「送信済みが Sent に残らない」の禁止。
- **受け入れ基準**:
  - [ ] 宛先が 1 件も無い、または形式不正な場合は送信せずエラーを返す。
  - [ ] 送信後、Sent フォルダに同一 Message-ID のメッセージが存在する。
  - [ ] SMTP 送信に失敗した場合は Sent に APPEND せず、エラーを返す。
  - [ ] From は設定されたアカウントのアドレス固定で、エージェントは変更できない。

### REQ-021: 返信

- **要件**: WHEN AI エージェントが返信元メッセージ ID と本文を指定して返信ツールを呼び出したとき, MCP サーバは In-Reply-To / References ヘッダを元メッセージに紐づけ、件名に `Re:` を付与し、宛先を元メッセージの From（全員返信指定時は To/Cc も含み自分を除く）として REQ-020 と同様に送信しなければならない。
- **理由**: スレッドを維持した返信。
- **受け入れ基準**:
  - [ ] In-Reply-To が元メッセージの Message-ID と一致する。
  - [ ] 既に `Re:` で始まる件名には重ねて付与しない。
  - [ ] 全員返信時に自分のアドレスが宛先に含まれない。

### REQ-022: 転送

- **要件**: WHEN AI エージェントが元メッセージ ID・転送先・コメントを指定して転送ツールを呼び出したとき, MCP サーバは件名に `Fwd:` を付与し、コメントの後に元メッセージのヘッダ要約とテキスト本文を引用した本文を REQ-020 と同様に送信しなければならない。
- **理由**: スコープ「返信・転送」。
- **受け入れ基準**:
  - [ ] 元メッセージの添付ファイルは転送されない（対象外）。転送本文に添付があった旨を記載する。
  - [ ] 既に `Fwd:` で始まる件名には重ねて付与しない。

### 1.4 整理

### REQ-030: 既読 / 未読の変更

- **要件**: WHEN AI エージェントがメッセージ ID を指定して既読または未読ツールを呼び出したとき, MCP サーバは IMAP の \Seen フラグを変更し、成功後に DynamoDB の既読状態を更新しなければならない。
- **理由**: スコープ「整理」。
- **受け入れ基準**:
  - [ ] IMAP 更新成功後に DynamoDB が更新される。
  - [ ] IMAP 更新失敗時は DynamoDB を変更せずエラーを返す。

### REQ-031: フォルダ移動

- **要件**: WHEN AI エージェントがメッセージ ID と移動先フォルダを指定して移動ツールを呼び出したとき, MCP サーバは IMAP でメッセージを移動し、成功後に DynamoDB のフォルダと UID を更新しなければならない。
- **理由**: スコープ「整理」。
- **受け入れ基準**:
  - [ ] 存在しない移動先フォルダを指定した場合はエラーを返し、何も変更しない。
  - [ ] 移動後、検索で新しいフォルダとして見つかる。
  - [ ] MOVE 非対応サーバでは移動元に \Deleted 付きで残るが、検索結果には現れない。

### REQ-032: ゴミ箱への移動

- **要件**: WHEN AI エージェントがメッセージ ID を指定して削除ツールを呼び出したとき, MCP サーバは REQ-031 と同じ手順で Trash 相当フォルダへ移動しなければならない。The system shall never issue IMAP EXPUNGE（完全削除）を行わない。
- **理由**: 決定済み事項「ゴミ箱へ移動のみ」。誤操作の復旧を可能にする。
- **受け入れ基準**:
  - [ ] 削除後、メッセージが Trash フォルダに存在する。
  - [ ] コードベースに EXPUNGE を発行する経路が存在しない（静的テストで検証）。

### REQ-033: フラグの付与 / 解除

- **要件**: WHEN AI エージェントがメッセージ ID を指定してフラグ付与または解除ツールを呼び出したとき, MCP サーバは IMAP の \Flagged フラグを変更し、成功後に DynamoDB のフラグ状態を更新しなければならない。
- **理由**: スコープ「整理」。
- **受け入れ基準**:
  - [ ] REQ-030 と同じ順序・失敗時の振る舞い。

### 1.5 予約送信

### REQ-040: 予約の作成

- **要件**: WHEN AI エージェントが送信日時（タイムゾーン付き ISO 8601）と REQ-020 と同じ送信内容を指定して予約ツールを呼び出したとき, MCP サーバは予約を `pending` 状態で DynamoDB に保存し、指定日時に 1 回だけ発火するスケジュールを登録し、予約 ID を返さなければならない。
- **理由**: スコープ「予約送信」。
- **受け入れ基準**:
  - [ ] 送信日時が現在時刻より過去、または 1 年より先の場合はエラーを返し、予約を作らない。
  - [ ] 宛先の検証は REQ-020 と同じ。
  - [ ] スケジュール登録に失敗した場合は DynamoDB の予約も残さない。

### REQ-041: 予約の一覧・取消

- **要件**: WHEN AI エージェントが予約一覧ツールを呼び出したとき, MCP サーバは予約 ID・状態（pending / sent / failed / cancelled）・送信予定日時・宛先・件名を返さなければならない。WHEN AI エージェントが予約 ID を指定して取消ツールを呼び出したとき, MCP サーバは `pending` の予約を `cancelled` に変更しスケジュールを削除しなければならない。
- **理由**: 予約の確認と誤予約の取消。
- **受け入れ基準**:
  - [ ] `pending` 以外の予約を取消しようとするとエラーを返す。
  - [ ] 取消後にスケジューラが発火しても送信されない。

### REQ-042: 予約の実行（ちょうど 1 回の送信）

- **要件**: WHEN 予約の送信日時にスケジュールが発火したとき, スケジューラは予約の状態を `pending` から `sending` へ条件付きで遷移させ、成功した場合のみ REQ-020 と同様に送信し、状態を `sent` に更新しなければならない。
- **理由**: 禁止事項「二重送信・送信漏れ」。
- **受け入れ基準**:
  - [ ] 同じ予約に対する発火が同時・重複しても SMTP 送信は 1 回だけ行われる（条件付き書込で検証）。
  - [ ] 送信後の Sent フォルダへの APPEND を含む。
  - [ ] 指定日時から 5 分以内に送信が開始される。

### REQ-043: 予約送信の失敗

- **要件**: IF 予約の送信処理が失敗した場合, THEN スケジューラは指数バックオフで最大 3 回まで再試行し、それでも失敗した場合は状態を `failed` にし失敗理由を保存しなければならない。
- **理由**: 送信漏れの検知を可能にする。
- **受け入れ基準**:
  - [ ] `failed` の予約は REQ-041 の一覧で失敗理由付きで確認できる。
  - [ ] 再試行中も送信は合計 1 回を超えない（`sending` 状態からの再開時は SMTP 送信済みかを判定する）。

### 1.6 MCP プロトコル・認証

### REQ-050: MCP Streamable HTTP エンドポイント

- **要件**: The MCP サーバ shall MCP 仕様の Streamable HTTP トランスポートで `initialize` / `tools/list` / `tools/call` を提供し、本書のツール群（検索・閲覧・フォルダ一覧・送信・返信・転送・既読/未読・移動・削除・フラグ・予約作成/一覧/取消）を公開しなければならない。
- **理由**: Claude Code / Claude Desktop から登録できる形態（specify.md 成功の定義）。
- **受け入れ基準**:
  - [ ] Claude Code に URL を登録して `tools/list` が成功する。
  - [ ] 各ツールの入力は JSON Schema で定義され、不正な入力は実行前に拒否される。
  - [ ] サーバはリクエスト間で状態を持たない（セッションはステートレス）。

### REQ-051: クライアント認証（OAuth 2.1）

- **要件**: IF リクエストに有効な OAuth 2.1 アクセストークン（Bearer）が含まれない場合, THEN MCP サーバは HTTP 401 と `WWW-Authenticate` ヘッダ（Protected Resource Metadata の所在）を返し、いかなるツールも実行してはならない。The MCP サーバ shall MCP Authorization 仕様に従い `/.well-known/oauth-protected-resource` を公開し、認可サーバとして Amazon Cognito を使用しなければならない。
- **理由**: 禁止事項「認証されていないクライアントからのツール実行」。Claude Desktop / Claude Code のコネクタ登録でブラウザログインが使える。
- **受け入れ基準**:
  - [ ] 認証ヘッダ無し・署名不正・期限切れ・audience 不一致のそれぞれで 401 が返り、ツール処理が呼ばれない。
  - [ ] Claude Code に URL を登録すると OAuth のブラウザログインが起動し、完了後に `tools/list` が成功する。
  - [ ] Cognito のユーザは開発者 1 名のみで、セルフサインアップは無効である。

### REQ-052: メールサーバ認証情報の隔離

- **要件**: The system shall IMAP / SMTP の認証情報を Secrets Manager からのみ読み込み、ツールの入出力・エラーメッセージ・ログに含めてはならない。
- **理由**: 成功の定義「認証情報がエージェントに漏れない」。
- **受け入れ基準**:
  - [ ] ツールのスキーマにパスワードを受け取る入力が存在しない。
  - [ ] 接続エラー時のメッセージにホスト名以外の接続情報が含まれない（テストで検証）。

## 2. 非機能要件

### NFR-001: コスト

- **要件**: The system shall 想定利用量（受信 100 通/日、ツール呼出 200 回/日、予約 10 通/日、同期 15 分間隔）において月額 5 USD 以内で稼働し、利用がない月はほぼゼロ（1 USD 未満）でなければならない。
- **受け入れ基準**:
  - [ ] design.md のコスト概算が 5 USD 以内である。
  - [ ] 常時起動リソース（Provisioned Concurrency、NAT Gateway、常時起動 DB）を使わない。

### NFR-002: データ保持

- **要件**: The system shall 同期したメールの生メッセージとメタ情報を受信日から 1 年で自動削除しなければならない。
- **受け入れ基準**:
  - [ ] S3 ライフサイクルルールと DynamoDB TTL が CDK で定義されている（CDK assertions で検証）。
  - [ ] 予約送信のレコードは `sent` / `failed` / `cancelled` になってから 90 日で自動削除される。

### NFR-003: IaC と環境分離

- **要件**: The system shall すべての AWS リソースを AWS CDK で定義し、`--context stage=dev|prod` でスタック名とパラメータを切り替えなければならない。
- **受け入れ基準**:
  - [ ] `npx cdk synth --all --context stage=dev` が成功する。
  - [ ] dev と prod でスタック名が異なる（CDK assertions）。

### NFR-004: セキュリティ

- **要件**: The system shall S3 バケットをパブリックアクセス遮断・暗号化とし、各 Lambda に最小権限の IAM ロールを付与し、シークレットは Secrets Manager で管理しなければならない。
- **受け入れ基準**:
  - [ ] S3 の BlockPublicAccess が全て有効（CDK assertions）。
  - [ ] MCP サーバの Lambda はスケジューラ用のリソースに書込権限を持たない等、役割ごとにロールが分かれている。
  - [ ] Secrets Manager の値がログに出力されない。

### NFR-005: 応答時間

- **要件**: The MCP サーバ shall 検索・フォルダ一覧・予約操作はコールドスタートを除き 2 秒以内、本文閲覧は 3 秒以内、送信・整理操作（IMAP / SMTP 往復を含む）は 10 秒以内に応答しなければならない。
- **受け入れ基準**:
  - [ ] 正常性テストで各ツールの応答時間を計測し上限内である。

### NFR-006: 正常性テスト

- **要件**: The system shall デプロイ後の環境に対して `npm run test:smoke` で主要ユースケース（認証、フォルダ一覧、検索、閲覧、予約作成と取消）を実行できなければならない。
- **受け入れ基準**:
  - [ ] `CDK_OUTPUTS_FILE` と `STAGE` から接続先を解決する。
  - [ ] dev 環境でテスト用の予約を作成・取消し、実メール送信を発生させない。

### NFR-007: テストと CI

- **要件**: The system shall ユニットテスト（IMAP / SMTP / AWS SDK をモック）を `npm test` で実行し、CI で通らない変更をマージしてはならない。
- **受け入れ基準**:
  - [ ] 憲法の TDD 手順に従い、各タスクがテストから始まる。
  - [ ] MIME 解析・検索条件の組立・状態遷移はモック無しの純粋ロジックとしてテストできる。

### NFR-008: 観測性

- **要件**: The system shall 同期ジョブと予約送信の失敗を CloudWatch Logs に構造化ログとして記録し、予約送信が `failed` になった場合にアラームを発報しなければならない。
- **受け入れ基準**:
  - [ ] ログにメール本文・認証情報を含めない。
  - [ ] `failed` 遷移でメトリクスが 1 増え、アラームが定義されている（CDK assertions）。

## 3. 対象外

- 複数ユーザ・複数メールアカウント、Web UI、添付ファイルの取得・送信、HTML メール作成、一斉送信、完全削除（EXPUNGE）。
- Gmail API / Microsoft Graph 等のベンダ固有 API。
- 全文検索（本文に対するキーワード検索）。検索対象はメタ情報（件名・差出人・宛先・日時・状態）のみ。
