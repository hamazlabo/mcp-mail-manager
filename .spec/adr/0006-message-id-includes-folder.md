# ADR-0006: メッセージ id をフォルダ込みで導出し、移動は「旧レコード削除 + 新レコード作成」にする

- **日付**: 2026-09-19
- **ステータス**: Accepted
- **関連要件**: REQ-001, REQ-003, REQ-010, REQ-031, REQ-032
- **関連憲法条項**: 2. サーバレス優先（DynamoDB 単一テーブル）、4. 最小の変更

## 文脈 (Context)

design.md 4 章は `id = sha256(Message-ID)` とし、「フォルダ移動しても同じアイテムが更新される」ことを利点としていた。prod の実機テスト（2026-09-19）で、自分宛に送ったメールは INBOX の受信コピーと INBOX.Sent の APPEND コピーが同じ Message-ID を持つため、後に同期した Sent 側のレコードが INBOX 側を上書きし、INBOX の検索に現れないことが分かった（照合ログ `INBOX known: 4, total: 6`、L-0021）。個人利用では自分宛メモや自分を Cc した送信が日常的にあり、ユーザは「両方のフォルダで見えること」を選んだ。

## 決定 (Decision)

`id = sha256("<Message-ID>:<folder>")`（Message-ID 無しは従来どおり `sha256("<folder>:<uidValidity>:<uid>")`）とし、1 フォルダ 1 レコードにする。ツールによる移動は IMAP 成功後に「新 id のレコードを作成（`s3Key` は元のまま）→ 旧レコードを削除」し、戻り値の `id` は新しい値になる。同期の照合でレコードを削除するときは生メッセージをそのレコードの `s3Key` で削除する。既存レコードの移行は行わない（id は不透明な文字列）。

## 検討した選択肢

| 選択肢 | 利点 | 欠点 | コスト影響 |
|--------|------|------|------------|
| A: id にフォルダを含める（採用） | 同一 Message-ID の複数コピーが全て検索できる。同期は「消えた UID を削除、現れた UID を追加」の単純な規則で一貫する | 移動でツールの戻り値の id が変わる。MCP 実行ロールは S3 に書けないため移動後は旧 id の生メッセージを参照し続け、次回同期で新 id の生メッセージが書かれると旧オブジェクトが孤立する（ライフサイクル 365 日で消える） | 孤立オブジェクト分の S3 保存（数十 KB / 移動）。無視できる |
| B: 現状維持（Message-ID のみ） | 移動で id が変わらない | 自分宛メールが INBOX 側で見えない。メーリングリストの自己コピー等も同様 | 0 |
| C: 1 レコードに複数の所在を持つ | 両方見える | 検索 GSI とツールの契約が複雑化。移動・削除の整合が難しい | 実装量大 |

## 結果 (Consequences)

- 良い点: 検索結果とメールボックスの実態が一致する。移動の実装が「削除 + 追加」で同期と同じ規則になる。
- 悪い点 / トレードオフ: `move_message` / `trash_message` の応答 `id` が変わる（ツールの説明に明記）。移動後の孤立した生メッセージはライフサイクルで回収する。移動で新レコード作成後に旧レコードの削除だけが失敗した場合、次回同期の照合が旧レコードと共にその `s3Key`（新レコードも参照）を削除し、本文が読めなくなる可能性がある（DynamoDB の単一 Delete 失敗という低確率事象。次にそのメッセージがクライアント側で移動されれば再取込される）。
- 既存データ: 旧方式の id で取り込まれたレコードはそのまま残るため、変更前に取り込んだ自分宛メールの INBOX コピーは再同期（同期状態と Message レコードの削除 → 初回同期のやり直し）しないと現れない。
- 憲法との関係: 準拠。
