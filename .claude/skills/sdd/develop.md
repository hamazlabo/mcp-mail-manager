# /sdd develop [T-xxx]

`.spec/task.md` に沿って、1 タスクを TDD で実装する。

## 前提

1. `.spec/constitution.md`, `specify.md`, `requirements.md`, `design.md`, `task.md` を読む。
   欠けているものがあれば「`/sdd init` を先に実行してください」と伝えて停止する。
2. `git status` で作業ツリーの状態を確認し、未コミットの変更があればユーザに知らせる。

## タスク選択

- 引数にタスク ID があればそのタスク。なければ task.md の最初の未完了（`[ ]`）タスク。
- 依存タスクが未完了なら実行せず、その旨を伝えて停止する。
- 選んだタスクの目的・対象ファイル・最初に書くテスト・完了条件をユーザに提示してから着手する。

## 実装 (TDD)

1. **Red**: 「最初に書くテスト」を書き、テストを実行して失敗することを確認する。失敗出力を確認できるまで実装に進まない。
2. **Green**: テストを通す最小限の実装を書く。求められていない機能・抽象を足さない。
3. **Refactor**: テストが通る状態を保ったまま整理する。自分の変更が生んだ未使用コードは削除する。
4. 完了条件に対応する追加テストがあれば同じサイクルで繰り返す。
5. 全テストを実行し、成功を確認する。

## 設計からの逸脱

実装中に design.md どおりに進められない・より良い方法があると判明した場合:

1. 作業を止め、理由と代替案をユーザに提示する。
2. 承認されたら `.spec/adr/NNNN-<slug>.md` を起票し、design.md の該当箇所と task.md を更新する。
3. その後、実装を再開する。

## 完了処理

1. task.md の該当タスクを `[x]` にし、「完了ログ」に完了日（今日の日付）と備考を追記する。
2. **知見の記録**: このタスクで得た「次回も使える発見」を [learn.md](learn.md) の手順で `.learn/` に記録する。対象の目安:
   - Red → Green で 2 回以上試行した原因（ライブラリの癖、モックの落とし穴、環境差）
   - design.md / task.md の記述が実装時に不足・不正確だった点
   - 手順書（init.md / develop.md）どおりに進めて非効率だった点
   - ドメイン固有の前提（メールプロトコル・API 制限など）
   該当がなければ記録しない。1 タスクで 0〜3 件が目安。
3. 変更ファイル一覧、実行したテストとその結果、次の未完了タスクをユーザに報告する。
4. `.learn/` に `status: new` の知見が 5 件以上あれば、報告の末尾で `/sdd upgrade` の実行を提案する。
5. コミットはユーザの指示があった場合のみ行う。

## 停止条件

- テストが通らないまま 3 回試行しても解決しない場合は、状況と仮説を報告して停止する。
- 憲法に反する実装が必要になった場合は、ADR 起票の承認を得るまで停止する。
