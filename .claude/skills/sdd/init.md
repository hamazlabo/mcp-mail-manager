# /sdd init <開発要望>

開発要望を起点に、憲法に従って spec 一式を対話的に作成する。
すでに `.spec/specify.md` などが存在する場合は、上書きせず「更新か再作成か」をユーザに確認する。

## 前提

1. `.spec/constitution.md` を読み、制約（AWS 前提 / サーバレス優先 / TDD）を把握する。
2. `README.md` と `CLAUDE.md` があれば読み、プロジェクトの文脈を把握する。
3. `.spec/templates/` の雛形を読む。

## ステップ 1: 上位ビジョンのヒアリング → specify.md

1. 開発要望（`$ARGUMENTS` の `init` 以降）を読み、雛形 `specify.md` の各節を埋めるのに足りない情報を洗い出す。
2. 不足分を AskUserQuestion でヒアリングする。目安となる質問:
   - 解決したい課題は何か、今どう困っているか
   - 利用者（Actor）は誰か
   - やらないこと（Out of scope）
   - 成功の定義
3. 回答をもとに `.spec/specify.md` を作成する。要望に含まれない点は推測せず「未決事項」として明記する。
4. 要点（一言要約・スコープ・成功の定義）をユーザに提示し、承認を得る。

## ステップ 2: 要件ヒアリング → requirements.md

1. specify.md の課題・スコープから、必要になりそうな要件を仮起こしする。
2. AskUserQuestion で「ざっくり」ヒアリングする。細部まで聞き切らず、次を確認する:
   - 主要ユースケース（正常系）の優先順位
   - 起きてはいけないこと（Unwanted behaviour）
   - 非機能要件（性能・コスト上限・可用性・セキュリティ）の水準
3. 回答をブラッシュアップし、EARS 構文で `.spec/requirements.md` を作成する。
   - すべての要件に一意 ID（REQ-xxx / NFR-xxx）と、テストで検証可能な受け入れ基準を付ける。
   - 憲法由来の非機能要件（例: アイドル時コスト、IaC 管理）は明示的に NFR として含める。
4. 要件一覧（ID とタイトル）と未決事項をユーザに提示し、承認を得る。

## ステップ 3: 技術要望ヒアリング → design.md

1. AskUserQuestion で技術要望をヒアリングする:
   - 言語・ランタイムの希望
   - 既存資産・既存 AWS アカウントの制約
   - 想定トラフィック・データ量（コスト概算に使う）
   - 特に守りたい非機能（レイテンシ・運用の手間など）
2. **提案を行う**: 憲法と requirements.md を照らし、ユーザの技術要望よりも優れた案があれば、理由・トレードオフ・コスト差とともに提案する。
   - 例: 常時起動 DB の希望に対して DynamoDB や Aurora Serverless v2 を提案する。
   - ユーザが元の希望を選んだ場合はそれを尊重し、憲法と外れるなら ADR に記録する。
3. 選定結果で `.spec/design.md` を作成する。
   - 技術スタック表には「検討した代替案」を必ず書く。
   - コスト概算、テスト戦略、要件トレーサビリティ表を埋める。
   - 重大な判断（コンピュート・データストア・認証方式・憲法例外）は `.spec/adr/NNNN-<slug>.md` を雛形から起票し、design.md からリンクする。番号は既存 ADR の最大値 + 1。
4. アーキテクチャ概要・スタック・コスト概算・ADR 一覧をユーザに提示し、承認を得る。

## ステップ 4: 実装計画 → task.md

1. design.md のコンポーネント・データモデル・IaC を、`/sdd develop` が 1 回の実行で完了できる粒度に分解する。
   - 1 タスク = 1 つの検証可能な成果。変更 300 行以内、テスト 1〜5 本が目安。
   - 各タスクに「最初に書くテスト」「完了条件」「対応要件」「依存」を必ず書く（TDD 前提）。
   - フェーズ 0 は必ず「テストランナーが動く足場」から始める。
2. 依存関係が上から順に解決される順序で並べ、`.spec/task.md` を作成する。
3. フェーズ構成とタスク数、最初の 3 タスクをユーザに提示する。

## 完了時

作成したファイル一覧と、次のアクション（`/sdd develop` の実行）を伝える。
