# /sdd upgrade

`.learn/` に蓄積した `status: new` の知見をレビューし、ステアリング（常時読み込まれる文書）へ反映してコンテキストのバージョンを上げる。
「記録は安価に、昇格は慎重に」が原則。1 回の upgrade で反映する変更は少数に絞る。

## 昇格先と編集可否

| 昇格先 | 編集 | 内容 |
|--------|------|------|
| `CLAUDE.md` | 可 | プロジェクト横断の規律・ハマりどころ |
| `.claude/skills/sdd/*.md` | 可 | 手順書の改善 |
| `.spec/templates/*.md` | 可 | 雛形に足りなかった項目 |
| `.spec/design.md` / `specify.md` / `requirements.md` | 可 | 技術事実・用語・要件の補正（要件変更は ADR も起票） |
| `.spec/constitution.md` | **不可** | 提案文を作成し、人間に適用を依頼する |

## 手順

### 1. 収集

1. `.learn/*.md` のうち `status: new` を全件読む。0 件なら「昇格対象なし」と報告して終了する。
2. `.learn/CHANGELOG.md` を読み、現在のコンテキストバージョンを把握する（存在しなければ v0）。

### 2. 分類と提案

1. 知見を「同じ昇格先・同じ主題」でグループ化する。
2. 各グループについて次を判定する:
   - **promote**: 2 回以上再現した、または今後確実に再発する。昇格先と具体的な追記文を作る。
   - **keep**: 有用だが一般化には事例不足。`.learn/` に残す。
   - **reject**: 一時的・誤り・既に文書化済み。理由を記録する。
3. 提案を表にしてユーザに提示し、AskUserQuestion で承認を得る（グループが多い場合は 4 件ずつ）。
   提示項目: 知見 ID、判定、昇格先、追記文（差分）、削除・書き換えが伴う場合はその旨。

### 3. 反映

承認されたグループについて:

1. 昇格先ファイルを編集する。既存の節に追記し、無関係な箇所は触らない。重複する記述があれば統合する。
2. 各知見ファイルの frontmatter を更新する: `status: promoted`、`promoted_to: <ファイルパス>`、`promoted_in: v<N+1>`。
   reject は `status: rejected` と `reason` を書く。
3. `.learn/CHANGELOG.md` に新バージョンの節を追加する:

   ```markdown
   ## v<N+1> (YYYY-MM-DD)

   - L-0003 → CLAUDE.md: <1 行要約>
   - L-0005, L-0007 → .claude/skills/sdd/develop.md: <1 行要約>
   - rejected: L-0004 (<理由>)
   ```

4. 憲法に関わる提案があれば、`.learn/CHANGELOG.md` の同バージョンに「憲法への提案」小節として追記文案を残し、ユーザに人間側での適用を依頼する。

### 4. 検証と報告

1. 編集した手順書・テンプレートに `{{}}` の壊れや表崩れがないことを確認する。
2. `git diff --stat` で変更ファイル一覧を出し、バージョン番号・昇格件数・keep 件数・reject 件数を報告する。
3. コミットはユーザの指示があった場合のみ行う。

## 実行タイミングの目安

- `status: new` が 5 件以上溜まったとき（`/sdd develop` が提案する）
- フェーズ（task.md の見出し単位）が完了したとき
- 手順書どおりに進めて同じ非効率を 2 回感じたとき
